¿Qué es y para qué sirve?

El conector Azure Monitor permite que el agente de Ruvic consulte métricas y alertas de tus recursos en Azure, en modo solo lectura. Una vez configurado, puedes pedirle al agente cosas como:

  • “¿Cómo ha estado el uso de CPU de mi máquina virtual en las últimas 6 horas?”
  • “¿Hay alguna alerta activa en mi suscripción de Azure ahora mismo?”
  • “Revisa las transacciones de mi cuenta de almacenamiento del último día.”

Operaciones soportadas:

Operación Qué hace
monitor.get_metrics Consulta los datapoints de una métrica de un recurso específico
monitor.list_active_alerts Lista las alertas que están actualmente activas en la suscripción
Solo lectura, por diseño El conector nunca crea, modifica ni elimina reglas de alerta, métricas o recursos: solo consulta. El Service Principal recomendado solo tiene el rol Monitoring Reader.

Prerrequisitos

  • Una suscripción de Azure con recursos que ya generen métricas o alertas.
  • Acceso a Azure AD (o al Azure CLI) para crear un Service Principal, solo durante la configuración inicial.
  • El ID de la suscripción de Azure a monitorear.

Configuración en el fabricante

Vas a crear un Service Principal dedicado de solo lectura para Ruvic. No reutilices una cuenta de usuario ni credenciales de otra aplicación.

  1. Crea el Service Principal con el rol Monitoring Reader.

    Con Azure CLI autenticado como administrador:

    az ad sp create-for-rbac --name "ruvic-monitor-reader" \
  --role "Monitoring Reader" \
  --scopes "/subscriptions/TU_SUBSCRIPTION_ID"
    Nota Para limitar el alcance a solo un grupo de recursos en vez de toda la suscripción, cambia --scopes a "/subscriptions/TU_SUB/resourceGroups/TU_GRUPO".
  2. Copia las credenciales generadas.

    El comando anterior imprime un JSON con appId (Client ID), password (Client Secret) y tenant (Tenant ID). Guárdalos: el Client Secret solo se muestra una vez.

    [ Captura: salida de az ad sp create-for-rbac con las credenciales — reemplazar por assets/img/azure-monitor-sp.png ]
  3. Verifica el acceso desde la línea de comandos.

    Inicia sesión con el Service Principal y consulta las alertas de la suscripción:

    az login --service-principal -u TU_CLIENT_ID -p TU_CLIENT_SECRET --tenant TU_TENANT_ID
az monitor metrics alert list --output table

    Si responde sin error de permisos (aunque no haya alertas), el fabricante quedó listo. Anota estos valores para la siguiente sección: Tenant ID, Client ID, Client Secret y Subscription ID.

Permisos requeridos

Principio de mínimo privilegio: el Service Principal de Ruvic solo necesita el rol Monitoring Reader. No otorgues Monitoring Contributor, Contributor ni Owner.

Rol RBAC Para qué sirve
Monitoring Reader Consultar métricas (monitor.get_metrics) y listar alertas activas (monitor.list_active_alerts). Rol 100% de solo lectura.

Configuración en Ruvic

Entra a Settings → Conectores, busca la tarjeta Azure Monitor y pulsa Configurar. Diligencia el formulario con los valores que obtuviste en la sección anterior:

Campo del formulario Valor
Tenant ID El tenant del paso 2
Client ID (Application ID) El appId del paso 2
Client Secret El password del paso 2. Se guarda cifrado como secreto: la interfaz no volverá a mostrarlo
Subscription ID El ID de la suscripción a monitorear
Timeout de conexión Opcional; 10 segundos por defecto

Guarda y pulsa Probar conexión — la plataforma verificará que el Service Principal pueda autenticarse.

[ Captura: formulario del conector Azure Monitor en Settings → Conectores — reemplazar por assets/img/azure-monitor-form.png ]

Verificación

  1. Test de conexión exitoso.

    El botón Probar conexión debe responder: “Conexión exitosa a Azure Monitor (suscripción ...)”. La tarjeta del conector cambia a estado Configurado.

  2. Automatización mínima de prueba.

    Abre una conversación nueva con el agente y pídele: “¿Hay alguna alerta activa en Azure Monitor en este momento?” El agente debe responder con el listado real de alertas (o confirmar que no hay ninguna). Si lo hace, el conector quedó operativo de punta a punta.

Solución de problemas

Mensaje / síntoma Causa probable y solución
“Credenciales inválidas o el Service Principal no tiene permiso suficiente” Client ID, Client Secret o Tenant ID mal copiados, o falta el rol Monitoring Reader. Reintenta los pasos 1 y 2 de la sección 3.
“No se pudo conectar a Azure AD … (timeout)” Tenant ID incorrecto, o hay un problema de red saliente hacia Azure.
“No se encontró el recurso o la métrica” El resource_id no es el ARM resource ID completo, o el nombre de la métrica no aplica a ese tipo de recurso. Verifica con az resource show --ids TU_RESOURCE_ID.
get_metric_data devuelve una lista vacía No es necesariamente un error: puede significar que no hubo actividad en ese rango de tiempo. Verifica el nombre exacto de la métrica en el Azure Portal → recurso → Métricas.
El conector aparece “Sin configurar” tras guardar Algún campo obligatorio quedó vacío. Ábrelo de nuevo y completa Tenant ID, Client ID, Client Secret y Subscription ID.

Preguntas frecuentes y notas de seguridad

¿El agente puede crear o modificar reglas de alerta?

No. El conector nunca llama a operaciones de escritura, y el Service Principal solo tiene el rol Monitoring Reader (solo lectura).

¿Dónde queda guardado el Client Secret?

Como secreto en el almacén de credenciales de la plataforma, asociado a tu usuario. La interfaz nunca vuelve a mostrarlo; solo indica “definida”. Para cambiarlo, escribe uno nuevo en el formulario; para conservarlo al editar otros campos, deja el campo vacío.

Rotación de credenciales

Recomendado cada 90 días o según tu política: genera un nuevo Client Secret en Azure AD → App Registration → "Certificates & secrets", actualízalo en el formulario del conector, prueba la conexión, y luego elimina el secreto anterior.

¿Qué hago si las credenciales se comprometen?

  1. Elimina el Client Secret comprometido de inmediato en Azure AD → App Registration → "Certificates & secrets".
  2. Revisa la actividad reciente del Service Principal en Azure AD → Sign-in logs.
  3. Genera un Client Secret nuevo y actualízalo en el formulario del conector.

¿Expiran las credenciales?

Sí — los Client Secrets de Azure AD tienen fecha de expiración definida al crearlos (por defecto 6-24 meses según el método usado). Configura un recordatorio para renovarlo antes de esa fecha, o el conector dejará de funcionar.

Buenas prácticas Usa siempre un Service Principal dedicado con el rol Monitoring Reader; restringe el scope a un grupo de recursos específico si solo necesitas monitorear ciertos recursos; anota la fecha de expiración del Client Secret; y evita compartir las credenciales por canales no seguros.
